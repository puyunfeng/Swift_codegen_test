# swift_codegen — turn Kotlin sealed types into Swift enums

A `sealed interface` in Kotlin Multiplatform degrades into a pile of Kotlin-exported classes on
the Swift side: all you can do is downcast with `if let x = value as? HelloTestHelloOneFun`, and
the compiler never tells you when a branch is missing. This project combines an annotation, a KSP
processor and a Gradle plugin to generate a native Swift `enum` at build time: one case per sealed
subtype (constructor parameters become associated values), plus a `toX()` method that turns the enum
back into a Kotlin object. Swift code can then use an exhaustive `switch`, and a forgotten branch
fails to compile.

## Example

On the Kotlin side you only annotate the sealed type (the annotation ships in
`swift_codegen_annotations`, which the plugin adds to `commonMainImplementation` for you):

```kotlin
package com.example.swift_codegen_test

import com.example.swift_codegen.GenerateSwiftEnum

@GenerateSwiftEnum
sealed interface HelloTestHello {
    object OneTab : HelloTestHello
    class OneFun(val s: String, val s2: String) : HelloTestHello
    class ThreeFun2(val s: String, val s2: Int, val s3: Boolean) : HelloTestHello
    class UserFun(val user: User) : HelloTestHello
}

data class User(val name: String)
```

After `./gradlew generateSwiftEnums`, `iosApp/iosApp/Generated/HelloTestHelloEnum.swift` contains:

```swift
// Generated by KSP from com.example.swift_codegen_test.HelloTestHello. Do not edit.
// Regenerate with: ./gradlew generateSwiftEnums
import SharedLogic

public enum HelloTestHelloEnum {
    case oneFun(s: String, s2: String)
    case oneTab
    case threeFun2(s: String, s2: Int32, s3: Bool)
    case userFun(user: User)

    public func toHelloTestHello() -> HelloTestHello {
        switch self {
        case let .oneFun(s, s2):
            HelloTestHelloOneFun(s: s, s2: s2)
        case .oneTab:
            HelloTestHelloOneTab.shared
        case let .threeFun2(s, s2, s3):
            HelloTestHelloThreeFun2(s: s, s2: s2, s3: s3)
        case let .userFun(user):
            HelloTestHelloUserFun(user: user)
        }
    }
}
```

On the Swift side it is an ordinary enum: `switch` is exhaustive, you can add `Identifiable`,
`Equatable` and friends, and `toHelloTestHello()` hands it back to shared code:

```swift
struct IntentListView: View {
    let intents: [HelloTestHelloEnum]

    var body: some View {
        List(intents.indices, id: \.self) { index in
            switch intents[index] {
            case .oneTab:
                Text("tab")
            case let .oneFun(s, s2):
                Text(s + s2)
            case let .threeFun2(s, s2, s3):
                Text("\(s) \(s2) \(s3)")
            case let .userFun(user):
                Text(user.name)
            }
        }
    }
}

// Hand it back to the Kotlin view model
func send(_ intent: HelloTestHelloEnum, to viewModel: ViewModel) {
    viewModel.onIntent(intent.toHelloTestHello())
}
```

> The mapping is one-way (Swift enum → Kotlin object). There is no generated
> Kotlin-instance → enum conversion; write that `if let` mapping yourself in Swift.

## Modules

| Module | Coordinates | Purpose |
| --- | --- | --- |
| `swift_codegen_annotations` | `com.example.swift_codegen:swift_codegen_annotations` | KMP library providing `@GenerateSwiftEnum` and `GenerateSwiftEnumMode` |
| `swift-codegen` | `com.example.swift_codegen:swift_codegen` | KSP processor that reads the annotation and writes the Swift files |
| `swift_codegen_gradle_plugin` | `com.example.swift_codegen:swift_codegen_gradle_plugin` | Gradle plugin `com.example.swift_codegen`, wiring the two above and registering `generateSwiftEnums` |

When it runs: the plugin adds the processor to every `kspIos*` configuration, and
`generateSwiftEnums` depends on the first available task among
`kspKotlinIosSimulatorArm64` → `kspKotlinIosArm64` → `kspKotlinIosX64`.

## Integration

Requires Kotlin Multiplatform, KSP, and at least one declared iOS target. The sample module
`sharedLogic` in this repo is wired exactly this way, so you can copy from it.

### 1. Configure the repositories

Artifacts are published to GitHub Packages
(`https://maven.pkg.github.com/puyunfeng/Swift_codegen_test`). `pluginManagement` resolves the
plugin marker, while `dependencyResolutionManagement` resolves the annotations and processor
dependencies the plugin injects, so both need the repository:

```kotlin
// settings.gradle.kts
pluginManagement {
    repositories {
        mavenLocal()
        maven {
            url = uri("https://maven.pkg.github.com/puyunfeng/Swift_codegen_test")
            credentials {
                username = providers.gradleProperty("gpr.user").orNull
                password = providers.gradleProperty("gpr.key").orNull
            }
        }
        google {
            mavenContent {
                includeGroupAndSubgroups("androidx")
                includeGroupAndSubgroups("com.android")
                includeGroupAndSubgroups("com.google")
            }
        }
        mavenCentral()
        gradlePluginPortal()
    }
}

dependencyResolutionManagement {
    repositories {
        mavenLocal()
        maven {
            url = uri("https://maven.pkg.github.com/puyunfeng/Swift_codegen_test")
            credentials {
                username = providers.gradleProperty("gpr.user").orNull
                password = providers.gradleProperty("gpr.key").orNull
            }
        }
        mavenCentral()
    }
}
```

Putting it before `google()` / `mavenCentral()` is fine: `google()` is already restricted by
`mavenContent` to the androidx / com.android / com.google groups, so it would never look up
`com.example.swift_codegen` anyway. And when no credentials are configured, Gradle gets a 401 from
this repository and simply tries the next one, so the build is not broken.

Credentials go into `~/.gradle/gradle.properties`:

```properties
gpr.user=<GitHub username>
gpr.key=<PAT with read:packages>
```

### 2. Version catalog (recommended)

Register the version and a plugin alias in `gradle/libs.versions.toml`:

```toml
[versions]
ksp = "2.3.13"          # pairs with Kotlin 2.4.21
swiftCodegen = "1.0.0"

[plugins]
ksp = { id = "com.google.devtools.ksp", version.ref = "ksp" }
swiftCodegen = { id = "com.example.swift_codegen", version.ref = "swiftCodegen" }
```

Using an alias instead of hardcoding `id("com.example.swift_codegen") version "1.0.0"` in every
module keeps the version in one place, so an upgrade touches a single line.

> In this repo `swiftCodegenVersion` in `gradle.properties` is the version the three libraries are
> **published** as, while `swiftCodegen` in `libs.versions.toml` is the version the sample
> **consumes**. The sample resolves the plugin from mavenLocal, so the two must match.

### 3. Apply the plugins

```kotlin
plugins {
    alias(libs.plugins.kotlinMultiplatform)
    alias(libs.plugins.androidMultiplatformLibrary)
    alias(libs.plugins.ksp)
    alias(libs.plugins.swiftCodegen)
}
```

The KSP version has to match your Kotlin version (2.3.13 for 2.4.21 here). The order relative to the
codegen plugin does not matter: the plugin hooks in lazily through `pluginManager.withPlugin`, so
either order works — KSP first is only convention. The processor and annotation dependencies are
injected by the plugin, so there is nothing to declare by hand.

### 4. Declare an iOS target

The generated file `import`s your framework, so the target and framework names have to line up:

```kotlin
kotlin {
    listOf(iosArm64(), iosSimulatorArm64()).forEach { target ->
        target.binaries.framework {
            baseName = "SharedLogic"   // matches swiftCodegen.swiftModuleName
            isStatic = true
        }
    }
}
```

### 5. Configure

```kotlin
swiftCodegen {
    // must equal the iOS framework's baseName, it is what the generated file `import`s
    swiftModuleName.set("SharedLogic")
    // relative to the repository root; inside an Xcode 16 synchronized folder, so it compiles
    outputSubDir.set("iosApp/iosApp/Generated")
}
```

### 6. Generate and hook it up in Xcode

```bash
./gradlew generateSwiftEnums
```

To see what was actually generated or skipped, or to force a re-run:

```bash
./gradlew generateSwiftEnums --info --rerun-tasks
```

`--info` is what surfaces the processor's own log lines (`[ksp] Generated <path>` /
`[ksp] Swift enum is already up to date`). `--info` alone usually shows nothing: when the inputs
have not changed, `kspKotlinIos*` is UP-TO-DATE and the processor never runs. `--rerun-tasks`
ignores the up-to-date checks, at the cost of re-running the whole chain (Kotlin/Native compile
plus KSP), so keep it for debugging rather than everyday builds.

Xcode only compiles files that belong to the target, and the generated `.swift` files are written
straight to disk by Gradle/KSP without touching the project file. That leaves two cases:

- **Xcode 16+ synchronized folders (this repo, `objectVersion = 77`)**: `iosApp/iosApp` is a
  `PBXFileSystemSynchronizedRootGroup`, so whatever lives inside the folder is compiled. Generating
  into `iosApp/iosApp/Generated` is picked up automatically and the project file stays untouched.
- **Older projects (files registered one by one in a group)**: add the generated directory to the
  target's Compile Sources **once**. Prefer a folder reference (choose *Create folder references*
  in Add Files, the blue folder) so files produced by newly annotated types are compiled
  automatically; with a plain group you have to add every new file again. With XcodeGen/Tuist,
  declare the directory in `sources`.

Re-running the generator does not break the reference: output paths are stable, and the processor
does not rewrite a file whose content is unchanged, so Xcode's incremental build is not disturbed.

## Configuration options

| Property | Default | Description |
| --- | --- | --- |
| `swiftModuleName` | `App` | Module name of the `import` in the generated file, usually the framework's `baseName` |
| `outputSubDir` | `iosApp/Sources/Generated` | Output directory, relative to the repository root |
| `swiftEnumMode` | `CONCURRENT` | `SEQUENTIAL` / `CONCURRENT`; concurrent writes require every annotation to target a distinct file |
| `swiftEnumSuffix` | `Enum` | Suffix appended to the interface name when `swiftEnumName` is not set |
| `swiftFormatPath` | empty | Path to the `swiftformat` executable; when empty it tries `PATH`, then `/opt/homebrew/bin`, then `/usr/local/bin`, and skips formatting if none is found |

## Annotation parameters

Empty string arguments on `@GenerateSwiftEnum` mean "inherit the global value".

| Parameter | Description |
| --- | --- |
| `swiftModuleName` | Overrides the global module name |
| `outputSubDir` | Overrides the global output directory |
| `swiftEnumName` | Full Swift enum name; defaults to `<interface name><swiftEnumSuffix>` |
| `mode` | Overrides the global `swiftEnumMode`; only applies when passed explicitly |

Case names come from the subtype's simple name: the `Intent` suffix is stripped and the first
letter lowercased (`OneFun` → `oneFun`); Swift keywords are wrapped in backticks automatically.

## Supported types

Subtypes must be `object` or `class`; a `class` needs a primary constructor whose parameter types
are all listed below (anything else is reported as an error and that subtype is skipped, leaving
the generated file incomplete):

| Kotlin | Swift |
| --- | --- |
| `String` | `String` |
| `Int` / `Long` / `Short` / `Byte` | `Int32` / `Int64` / `Int16` / `Int8` |
| `Boolean` / `Double` / `Float` | `Bool` / `Double` / `Float` |
| `Char` | `Character` |
| `List<T>` / `Array<T>` / `Collection<T>` / `Iterable<T>` | `[T]` |
| `Set<T>` | `Set<T>` |
| `Map<K, V>` | `[K: V]` |
| `T?` | `T?` |
| Any other class (including `@ObjCName`) | The matching Swift name; nested classes are prefixed with the outer name |

## Limitations

- Only sealed classes/interfaces are supported; enum-class subtypes (`enum class`) are not.
- One annotation produces one file, named `<swiftEnumName>.swift`.
- With `CONCURRENT`, every annotated type must write to a distinct file, otherwise they overwrite
  each other.
- The output directory has to sit where Xcode compiles it: synchronized-folder projects (this repo,
  Xcode 16+) work out of the box; older projects need the one-time registration described in
  "Generate and hook it up in Xcode".
- The annotation/processor versions injected by the plugin always equal the plugin's own version
  (they are released together), so upgrade all three together.
